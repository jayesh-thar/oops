==============================================================
JAVA OOP - TOP 10 INTERVIEW QUESTIONS (SIMPLE ANSWERS)
==============================================================
Format for each question:
  Q      : the question
  Answer : short, interview-ready answer (say this first)
  Explain: simple language explanation
  Example: small Java code with output (where useful)
  Trap   : common mistake or follow-up the interviewer may ask


--------------------------------------------------------------
Q1. What is OOP? What are its 4 pillars?
--------------------------------------------------------------
Answer:
  OOP (Object-Oriented Programming) is a way of writing programs
  using objects that hold data (fields) and behaviour (methods).
  The 4 pillars are Encapsulation, Abstraction, Inheritance and
  Polymorphism.

Explain:
  - Encapsulation : hide data, allow access only through methods
                    (private fields + public methods).
  - Abstraction   : show WHAT it does, hide HOW it does it
                    (abstract class, interface).
  - Inheritance   : child class reuses parent's code (extends).
                    It is an IS-A relationship (Dog IS-A Animal).
  - Polymorphism  : same method name, different behaviour
                    (overloading, overriding).

  Real-life example: a car.
    Encapsulation -> engine is hidden inside, you use the pedals.
    Abstraction   -> you press accelerate, you don't know the
                     fuel injection details.
    Inheritance   -> SportsCar is a Car, it reuses Car features.
    Polymorphism  -> "start()" works for petrol, diesel, electric
                     cars, each in its own way.

Trap:
  "Is Java 100% object-oriented?" -> No. Java has 8 primitive types
  (int, char, boolean, etc.) which are not objects, and static
  members work without an object.

Q2. What is the difference between a class and an object?
     What is a reference variable?
--------------------------------------------------------------
Answer:
  A class is a blueprint. An object is a real instance of that
  blueprint, created in heap memory using the new keyword.
  A reference variable stores the address of the object, not the
  object itself.

Explain:
  Class  = house plan (design only).
  Object = actual house built from the plan.
  One class can create many objects, each with its own data.

  Student s1 = new Student();
    - "Student s1"   -> reference variable (remote control)
    - "new Student()"-> object created in heap
    - "="            -> address of the object stored in s1

Example:
  Student s1 = new Student();
  s1.name = "Jayesh";
  Student s2 = s1;        // copies the REFERENCE, not the object
  s2.name = "Rahul";
  System.out.println(s1.name);

  Output:
  Rahul

  Why: s1 and s2 point to the SAME object, so a change through
  one is visible through the other.

Trap:
  - Calling a method on a null reference gives NullPointerException.
  - Fields get default values (0, false, null), but local
    variables do NOT, using them unassigned is a compile error.

Q3. What is a constructor? Can it be inherited or overridden?
--------------------------------------------------------------
Answer:
  A constructor is a special block that runs automatically when an
  object is created and initialises it. It has the same name as the
  class and no return type. It can be overloaded, but it can NOT be
  inherited or overridden.

Explain:
  - If you write no constructor, the compiler adds a default
    (empty, no-argument) constructor.
  - The moment you write ANY constructor, the compiler stops adding
    the default one.
  - this(...)  calls another constructor of the same class
                (constructor chaining, must be the first line).
  - super(...) calls the parent constructor (must be the first line).
  - If you don't write super(...), the compiler adds super(); itself.

Example:
  class Animal {
      Animal() { System.out.println("Animal constructor"); }
  }
  class Dog extends Animal {
      Dog() { System.out.println("Dog constructor"); }
  }
  new Dog();

  Output:
  Animal constructor
  Dog constructor

  Why: parent part of the object is built first, then the child.

Trap:
  - void Student() { }  is NOT a constructor. It has a return type,
    so it is a normal method (compiles fine, classic trick).
  - If the parent has only a parameterized constructor, the child
    must call super(args) explicitly, otherwise compile error.
  - A constructor can be private (used in Singleton).

Q4. What is the difference between method overloading and
     method overriding?
--------------------------------------------------------------
Answer:
  Overloading: same method name, different parameters, in the same
  class, decided at compile time.
  Overriding: child class gives its own version of a parent method
  with the same name and same parameters, decided at runtime.

Explain:
  +-------------------+----------------------+---------------------+
  |                   | Overloading          | Overriding          |
  +-------------------+----------------------+---------------------+
  | Where             | same class           | parent + child      |
  | Parameters        | must be different    | must be same        |
  | Binding           | compile time         | runtime             |
  | Needs inheritance | no                   | yes                 |
  | Return type       | can differ           | same or subtype     |
  +-------------------+----------------------+---------------------+

Example (overloading):
  int    add(int a, int b)       { return a + b; }
  double add(double a, double b) { return a + b; }

  add(2, 3)      -> 5
  add(2.5, 3.5)  -> 6.0

Example (overriding):
  class Animal { void sound() { System.out.println("Animal sound"); } }
  class Dog extends Animal {
      @Override
      void sound() { System.out.println("Bark"); }
  }

Trap:
  - Changing ONLY the return type is NOT overloading, it is a
    compile error.
  - Always write @Override so the compiler catches typos.

Q5. What is runtime polymorphism (dynamic method dispatch)?
--------------------------------------------------------------
Answer:
  When a parent reference points to a child object and an
  overridden method is called, the JVM decides at runtime which
  version to run, based on the ACTUAL OBJECT, not the reference type.

Explain:
  Reference type decides what you are ALLOWED to call.
  Object type decides WHICH VERSION actually runs.

Example:
  class Animal { void sound() { System.out.println("Animal"); } }
  class Dog extends Animal {
      void sound() { System.out.println("Dog barks"); }
      void fetch() { System.out.println("Dog fetches"); }
  }

  Animal a = new Dog();   // upcasting
  a.sound();              // Output: Dog barks
  a.fetch();              // COMPILE ERROR: Animal has no fetch()
  ((Dog) a).fetch();      // OK after downcasting

Why it matters:
  One loop can handle Dog, Cat, Cow... through an Animal array.
  Add a new animal tomorrow and the loop code does not change.

Trap:
  - Wrong downcast (Animal that is really a Cat cast to Dog) gives
    ClassCastException at runtime. Use instanceof to check first.
  - Fields are NOT polymorphic. If Parent and Child both have a
    field x, then  Parent p = new Child();  p.x  gives the PARENT's x.

Q6. Why does Java not support multiple inheritance with classes?
     How do we achieve it then?
--------------------------------------------------------------
Answer:
  To avoid the diamond problem (ambiguity). Java allows only one
  parent class, but a class can implement multiple interfaces.

Explain:
  Suppose B and C both extend A, and both override show().
  If D extends B and C, which show() should D get? It is
  ambiguous. Java blocks this by allowing only one parent class.

  Interfaces are safe because they traditionally only declare
  methods (no state, no body), so there is nothing conflicting
  to inherit.

Example:
  interface Flyable   { void fly(); }
  interface Swimmable { void swim(); }

  class Duck implements Flyable, Swimmable {
      public void fly()  { System.out.println("Duck flies"); }
      public void swim() { System.out.println("Duck swims"); }
  }

Trap:
  Since Java 8, interfaces can have default methods. If two
  interfaces have the same default method, the class MUST override
  it and can pick one using  InterfaceName.super.method();

Q7. What is the difference between an abstract class and an
     interface? (MOST ASKED)
--------------------------------------------------------------
Answer:
  An abstract class is a common base with shared code and state
  for closely related classes. An interface is a contract that
  defines a capability any class can adopt.

Explain:
  +------------------------+--------------------+-------------------+
  |                        | Abstract class     | Interface         |
  +------------------------+--------------------+-------------------+
  | Keyword                | extends            | implements        |
  | Multiple inheritance   | no (only one)      | yes (many)        |
  | Methods                | abstract + normal  | abstract, plus    |
  |                        |                    | default/static    |
  | Fields                 | any kind           | only constants    |
  |                        |                    | (public static    |
  |                        |                    | final)            |
  | Constructor            | yes                | no                |
  | Relationship           | IS-A               | CAN-DO            |
  +------------------------+--------------------+-------------------+

  When to use what:
    - Related classes sharing code/state  -> abstract class
      (Animal -> Dog, Cat)
    - Unrelated classes sharing a skill   -> interface
      (Bird, Plane, Drone can all be Flyable)

Example:
  abstract class Animal {
      abstract void sound();      // no body, child must implement
      void sleep() { System.out.println("Sleeping..."); }
  }

  interface Payment { void pay(); }

Trap:
  - You cannot create an object of an abstract class or interface,
    but you CAN create a reference of that type pointing to a
    child object:  Payment p = new UpiPayment();
  - A child must implement ALL abstract methods, or be abstract too.
  - abstract cannot be combined with final, private or static.

Q8. What is the difference between encapsulation and abstraction?
--------------------------------------------------------------
Answer:
  Encapsulation is hiding data and protecting it with access
  control (HOW you protect). Abstraction is hiding the
  implementation and showing only essential features (WHAT you show).

Explain:
  Encapsulation: ATM machine. You cannot touch the cash vault, you
  only use buttons, and the machine validates your request.
  Abstraction: you press "withdraw", you don't need to know how the
  bank's server processes it.

  Encapsulation works at the DATA level (private fields).
  Abstraction works at the DESIGN level (abstract class, interface).

Example (encapsulation):
  class Student {
      private int age = 20;

      public void setAge(int a) {
          if (a > 0) { age = a; }      // validation
      }
      public int getAge() { return age; }
  }

  s.age = -10;      -> COMPILE ERROR (private)
  s.setAge(21);     -> allowed, validated

Trap:
  - Getters and setters WITHOUT validation are no better than a
    public field. The value of encapsulation is CONTROL.
  - If a getter returns a mutable object (List, Date) directly,
    the caller can modify your internal data. Return a copy.

Q9. Explain the access modifiers in Java.
--------------------------------------------------------------
Answer:
  Java has 4 access levels: private, default (no keyword),
  protected and public. They control who can access a class,
  field, method or constructor.

Explain:
  +-----------+------------+--------------+-----------------+-----------+
  | Modifier  | Same class | Same package | Subclass (other | Everywhere|
  |           |            |              | package)        |           |
  +-----------+------------+--------------+-----------------+-----------+
  | private   | yes        | no           | no              | no        |
  | default   | yes        | yes          | no              | no        |
  | protected | yes        | yes          | yes (inheritance)| no       |
  | public    | yes        | yes          | yes             | yes       |
  +-----------+------------+--------------+-----------------+-----------+

  Memory trick: private < default < protected < public.

Trap:
  - Top-level classes can only be public or default.
    private/protected top-level class is not allowed.
  - One file can have only one public class, and the file name
    must match it.
  - Default is also called package-private.
  - protected in another package: the subclass can access it only
    through inheritance (its own object), not through a plain
    parent-type reference.

Q10. Can we override static, private and final methods?
      What happens with fields in inheritance?
--------------------------------------------------------------
Answer:
  No. final methods cannot be overridden, private methods are not
  visible to the child, and static methods are hidden, not
  overridden. Fields are never overridden, they are hidden.

Explain:
  - final   : the method is locked, override gives a compile error.
  - private : child cannot see it, a same-named child method is a
              completely NEW method.
  - static  : belongs to the class, not the object. The method that
              runs depends on the reference type (method hiding).
  - Only instance methods are polymorphic. Fields are not.

Example (field hiding):
  class Parent { int x = 10; }
  class Child extends Parent { int x = 20; }

  Parent p = new Child();
  System.out.println(p.x);            // Output: 10
  System.out.println(((Child) p).x);  // Output: 20

  Why: for fields, the REFERENCE type decides, not the object.

Rules of overriding to remember:
  1. Same name and same parameters.
  2. Return type same, or a subtype (covariant return).
  3. Access cannot be more restrictive (public cannot become
     private, but it can widen).
  4. Cannot throw broader checked exceptions than the parent.
  5. Always use @Override.


==============================================================
QUICK REVISION (ONE LINERS)
==============================================================
- Class = blueprint, Object = instance in heap, reference = remote.
- Constructor: same name as class, no return type, not inherited.
- Overloading = compile time, Overriding = runtime.
- Object decides which method runs, reference decides what you can call.
- No multiple inheritance with classes (diamond), use interfaces.
- Abstract class = shared code (IS-A), Interface = capability (CAN-DO).
- Encapsulation = protect data, Abstraction = hide implementation.
- Access: private < default < protected < public.
- Static / private / final methods cannot be overridden.
- Fields are hidden, not overridden.
